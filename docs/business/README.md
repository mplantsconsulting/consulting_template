# business — 事業・業務理解

## 目的

クライアントの事業構造・業務フロー・既存ルールを、**確定した事実として**記録する。
分析と施策検討の共通の土台となる場所。**ここが揺れると下流がすべて揺れる。**

## 情報源の階層

**業務の正は一次資料である。** それ以外の資料は、格が違う。
「何を事実として引用してよいか」はここで決まる。

| 階層 | 何か | 扱い |
|---|---|---|
| **一次** | クライアントが対外的に負う義務・行使できる権利が書かれた文書<br>（契約書・約款・規程・重要事項説明書・公開IR・法令） | **正。** 事実として引用してよい |
| **二次** | クライアントから提供された**生データ** | 実在するデータだが、**抽出条件・スコープが未確認**。<br>列構成は事実、母数は不明 |
| **三次** | 社内の**手順書・マニュアル・仕様書・過去の成果物・RPA/OCR等のコード** | **業務フローの根拠にしない。**<br>「〈誰か〉がこう作った／こう理解していた」までしか言えない |
| **参考** | 業界の標準形・一般論からの推定 | **事実ではない。** ヒアリング項目の下敷きにのみ使う |

### 三次資料の扱いについて（重要）

社内の手順書・過去の成果物には、**提案止まりのもの、試作段階で終わったもの、
運用に乗ったが既に使われていないものが混在しうる。**

- 手順書に書かれた工程が、現在の業務にそのまま存在するとは限らない
- **コードが読めることは、それが稼働していることの証明にならない**
- したがって読み取った内容は「**業務がこうである**」ではなく
  「**〈誰か〉がこう作った／こう理解していた**」としてのみ記録する

三次資料の記述を業務フローの根拠として引用する場合は、**先にクライアントへ確認を取ること。**
ファイル名を `ref_pj_` で始めるのは、この区別を名前で見えるようにするため。

### 一次資料についての注意

**規程・約款は「できること・義務」であって「やっていること」ではない。**
条項に書かれていても、実際にその運用が行われているかは**必ず別に確認する。**
（例: 遅延損害金の料率が規程にあっても、実際に請求されている割合は別の事実である）

## 置くもの

- 事業構造（商材、料金・課金体系、顧客セグメント、チャネル）
- 業務フロー（受注 → 提供 → 請求 → 入金 → 対応 → 終了 など、案件のテーマに沿った一連の流れ）
- 既存の社内ルール・基準・運用
- 用語・KPI の定義（社内で使われている定義）
- システム・データの所在（どのテーブルに何があるか）

## 置かないもの

- 分析結果や数値の集計 → [analysis/](../analysis/)
- 「こうすべき」という提案 → [ideas/](../ideas/)
- 他社の事例 → [cases/](../cases/)
- 問題の構造化・戦略レベルの整理 → [strategy/](../strategy/)

## 各ファイルの必須記載事項

```markdown

一次なら資料名・版・取得日・URL。三次ならフォルダパスと作成時期。

## 最終確認日
YYYY-MM-DD

## 内容
```

## 運用ルール

1. **事実と仮説を混ぜない。** 未確認の内容を書く場合は `【仮説・未確認】` を行頭に付け、**確認方法と確認担当を併記する。** 確認が取れた時点でタグを外し、情報源を追記する。
2. **一次情報を優先する。** 業務フローの記述は一次資料を根拠にする。三次資料しか根拠がない記述は、そのことを明記する。
3. **規程は「できること／義務」であって、運用の実態ではない。** 実際にそう運用されているかは別に確認する。
4. **用語の定義は1ファイルに集約する。** 主要な語の定義が文書ごとにブレると、分析結果が比較不能になる。定義変更は用語ファイルを更新し、影響する分析にリンクを張る。
5. 新規作成・更新したら [INDEX.md](../INDEX.md) に登録する。
