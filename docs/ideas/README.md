# ideas — 施策アイデア

## 目的

課題を解決する施策の候補を、検討・比較できる形で蓄積する。
**採否の決定はここでは行わない。** 決定するのはコンサルタント本人であり、このフォルダは**判断材料を揃える場所**である。

## 起案の前に確かめること

**施策の根拠が、次のいずれかであることを先に確かめる。**

- クライアントの一次資料（契約書・約款・規程など）→ [business/](../business/)
- クライアントへのヒアリングで確認が取れた事実 → [business/](../business/)
- 定量分析の結果（ステータス `完了`）→ [analysis/](../analysis/)

**三次資料（社内の手順書・過去の成果物・既存のコード）は、
ヒアリングの叩き台にはなるが、施策の根拠にはならない。**

> **コードが読めることは、それが稼働していることの証明にならない。**
> 手順書に書かれた工程が、いま現場に存在するとは限らない。

根拠が三次資料だけの施策は、起案せずに [client-qa/](../client-qa/) の確認事項に回す。
（この確認を飛ばすと、裏付けのない施策を提案し、指摘されて全部取り下げることになる。）

## 置くもの

- 施策候補1件につき1ファイル
- **見送った施策も削除せず残す**（見送り理由が次の検討で効く）

## 置かないもの

- 施策の根拠となる数値分析そのもの → [analysis/](../analysis/) に置き、ここからリンクする
- 問題の構造化・論点整理 → [strategy/](../strategy/)

## 命名規則：起案者ごとのディレクトリ

**施策は起案者ごとのディレクトリに分ける。** 複数人が同時に起案する運用では、共有の連番台帳を都度確認して採番するコストが高く、衝突・上書きの原因になる。起案者内で完結する連番にすることでこれを避ける。

```
docs/ideas/<起案者名>/IDEA-NNN_<施策名>.md    例: docs/ideas/hirose/IDEA-003_prepayment_incentive.md
```

- `<起案者名>` は [analysis/](../analysis/) と同じ識別子を使う。
- `NNN` は**起案者ディレクトリ内で**連番。他の起案者の採番とは独立でよい（衝突しない）。採番済みの番号は再利用しない。
- 施策IDそのものは `IDEA-NNN`（起案者名を含まない）。案件横断で引用するときは `hirose/IDEA-003` のように起案者ディレクトリ名を添えて曖昧さをなくす。

雛形: [_TEMPLATE.md](_TEMPLATE.md)。自分のディレクトリにコピーして採番する。自分のディレクトリがなければ作成する。

## ステータス

ファイル冒頭に必ず記載する。

| ステータス | 意味 |
|---|---|
| `draft` | 書きかけ。他者の参照対象外 |
| `検討中` | 判断材料を収集中 |
| `提案済` | 意思決定者に提示済み、回答待ち |
| `採用` | 実施決定 |
| `見送り` | 不採用（**理由の記載必須**） |
| `保留` | 前提条件が整うまで凍結（**解除条件の記載必須**） |

**`採用` `見送り` への変更は意思決定者の判断を受けてのみ行う。** アシスト作業として勝手に遷移させない。

## 運用ルール

1. **効果を断定しない。** 「〜が期待できる」ではなく「**〜という前提が成り立てば〜**」と条件付きで書く。
2. **根拠のない効果見込みの数値を書かない。** 試算する場合は前提を明記する。
3. **未確認事項を空欄にしない。** 何もなければ「なし（確認済み）」と書く。空欄は「検討していない」と区別がつかない。
4. **測定できないなら「測定できない」と書く。** 効果を測れない施策は、そのことを明示して提示する。
5. 施策同士が排他・依存関係にある場合は相互にリンクする。
6. 新規作成・ステータス変更したら [INDEX.md](../INDEX.md) に反映する。
