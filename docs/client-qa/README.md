# client-qa — 先方とのやり取り

## 目的

**先方とのやり取りの記録・集約先。** 発信元・内容によって3種類を扱う。

| 種別 | 発信元 | 内容 |
|---|---|---|
| `質問（送付）` | こちら → 先方 | **データだけでは決着しない項目**を、先方に投げられる形に整理したもの |
| `質問（受領）` | 先方 → こちら | 先方から受けた質問と、それへの返答 |
| `要望・FB` | 先方 → こちら | 先方から後から追加された要望・フィードバック（スコープ変更・優先度変更の申し入れを含む） |

各分析の「未確認事項」欄、[strategy/](../strategy/) の空欄一覧、
[data-dictionary/](../data-dictionary/) の「分かっていないこと」の**集約先**でもあり、
やり取りの結果は上流（[business/](../business/) [data-dictionary/](../data-dictionary/) [ideas/](../ideas/)）へ反映する。

> **確認事項・やり取りの記録は成果物である。**
> 「分からなかったこと」を答えやすい形で持ち帰らせるのも、先方の発言を後から追える形で残すのも、コンサルタントの仕事の一部であって手抜きではない。
> 確認事項のない提案は、確認していないだけである。記録のない要望対応は、言った言わないの元になる。

## 命名・採番

**1ファイル＝1回のやり取り（往復を含む）。** `QA-NNN_<内容>.md` で採番する。雛形: [_TEMPLATE.md](_TEMPLATE.md)

- `NNN` は種別を問わず通し番号。発生順に並べることを優先し、種別ごとの連番は作らない。
- ファイル冒頭の**種別**フィールドで `質問（送付）` `質問（受領）` `要望・FB` を明示する。
- 1ファイルに複数の論点を含めてよいが、**すべて同一種別・同一のやり取りの範囲内に限る。** 種別が混ざる場合は分割する。

## 運用ルール

### 共通

1. ステータスは種別ごとに異なる（下記）。**ステータスの変更履歴は消さず、更新履歴に積む。**
2. **回答・返答は日付と回答者/返答者を明記する。** 口頭でのやり取りも同様（**出所のない事実を作らない**）。
3. **やり取りが来たら、このフォルダで完結させない。**

   | 内容 | 反映先 |
   |---|---|
   | 業務の事実 | [business/](../business/) を更新し、`【仮説・未確認】` を外す |
   | 列・値の定義 | [data-dictionary/](../data-dictionary/) を更新 |
   | 指標の社内定義 | [data-dictionary/](../data-dictionary/) の定義台帳を更新 |
   | 塞がっていた分析 | 該当 [analysis/](../analysis/) の「未確認事項」から消し、**結果を見直す** |
   | スコープ・優先度への要望 | [strategy/](../strategy/) [ideas/](../ideas/) の該当箇所に反映し、変更履歴を残す |

   反映先は各ファイル末尾の「社内メモ」表に対応づけておく。

### `質問（送付）` — こちらから先方へ

1. **回答負荷を最優先で設計する。**
   - **選択肢へのチェックか、単語1つで答えられる形にする。**
   - 1回の照会は**20問を超えない。**
   - **調査が必要なものは質問にせず**「データ追加提供のお願い」として分離する。
2. **「分からない」の選択肢を必ず置く。** **推測で埋められるのが最も困る**ため。
   「担当が別」「未定」も同様に用意する。
3. **優先順位を先頭に置く。** 「まずこの5問だけでも回答が得られれば主要な詰まりが解ける」を明示する。
   全問への回答を待つと止まる。
4. ステータス: `未送付` → `送付済` → `一部回答` → `回答済`。

### `質問（受領）` — 先方からこちらへ

1. **受けた質問は改変せず原文のまま記録する。** 意図の解釈が必要な場合は「こちらの解釈」を別項目として添える。
2. **即答できない質問は、確認中である旨を先方に伝えたことを記録する。** 放置しない。
3. ステータス: `受領` → `確認中` → `回答済`。

### `要望・FB` — 先方からこちらへ

1. **要望・フィードバックも原文（または要旨）をそのまま記録する。** 「意訳して薄める」ことをしない。
2. **スコープ・進め方・判定基準に影響する要望は、影響先を明記する。** 影響先の運用ルール（[analysis/](../analysis/README.md) の「判定基準は結果を見た後に変えない」等）と衝突する場合は、その旨をこのファイルに明記した上で対応する。
3. **対応するか否かを勝手に決めない。** 対応方針は意思決定者（コンサルタント本人）の判断を受けてから「対応状況」欄を埋める。
4. ステータス: `受領` → `検討中` → `対応済` / `対応見送り`（**見送りは理由の記載必須**）。
