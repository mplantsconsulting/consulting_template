# client-qa — 先方への確認事項

## 目的

**データだけでは決着しない項目**を、先方に投げられる形に整理して置く場所。
各分析の「未確認事項」欄、[strategy/](../strategy/) の空欄一覧、
[data-dictionary/](../data-dictionary/) の「分かっていないこと」の**集約先**であり、
回答が来たら上流（[business/](../business/) [data-dictionary/](../data-dictionary/)）へ反映する。

> **確認事項は成果物である。**
> 「分からなかったこと」を答えやすい形で持ち帰らせるのは、コンサルタントの仕事の一部であって手抜きではない。
> 確認事項のない提案は、確認していないだけである。

## 運用ルール

1. **1ファイル＝1回の照会。** `QA-NNN_<内容>_<回次>.md` で採番する。雛形: [_TEMPLATE.md](_TEMPLATE.md)
2. **回答負荷を最優先で設計する。**
   - **選択肢へのチェックか、単語1つで答えられる形にする。**
   - 1回の照会は**20問を超えない。**
   - **調査が必要なものは質問にせず**「データ追加提供のお願い」として分離する。
3. **「分からない」の選択肢を必ず置く。** **推測で埋められるのが最も困る**ため。
   「担当が別」「未定」も同様に用意する。
4. **優先順位を先頭に置く。** 「まずこの5問だけでも回答が得られれば主要な詰まりが解ける」を明示する。
   全問への回答を待つと止まる。
5. ステータスは `未送付` → `送付済` → `一部回答` → `回答済`。
6. **回答が来たら、このフォルダで完結させない。**

   | 回答の種類 | 反映先 |
   |---|---|
   | 業務の事実 | [business/](../business/) を更新し、`【仮説・未確認】` を外す |
   | 列・値の定義 | [data-dictionary/](../data-dictionary/) を更新 |
   | 指標の社内定義 | [data-dictionary/](../data-dictionary/) の定義台帳を更新 |
   | 塞がっていた分析 | 該当 [analysis/](../analysis/) の「未確認事項」から消し、**結果を見直す** |

   反映先は各QAファイル末尾の「社内メモ」表に対応づけておく。
7. **回答は回答日と回答者を明記する。** 口頭回答も同様（**出所のない事実を作らない**）。
