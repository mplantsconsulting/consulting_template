# analysis — データ分析

## 目的

対象の実態を数値で把握し、施策の判断材料を提供する。
ここに置かれるのは **「事実と、その事実をどう導いたか」** であり、施策の是非の結論ではない。

## 進め方：計画を先に書き、結果を後から埋める

**1ファイル＝1つの問い。同じファイルを計画 → 結果 の順に育てる。**
結果を見てから問いや判定基準を書き換えると、都合のよい解釈が後付けで通ってしまう。それを構造的に防ぐための運用。

```
① 計画を書く         問い・データソース・前提・手法・判定基準 を先に埋める
        ↓            → ステータス: 計画中
② 計画を確定させる    判定基準まで書けた時点で確定。以降、判定基準は原則いじらない
        ↓            → ステータス: 計画確定
③ 集計する           手法どおりに実行。計画との差異が出たら「計画との差異」欄に記録
        ↓            → ステータス: 検証中
④ 結果と解釈を埋める  判定基準に照らして書く
                     → ステータス: 完了
```

- **③で計画どおりに集計できないと分かるのは正常。** 黙って手法を変えず、「計画との差異」に理由を書いてから変える。
- **④で結果が仮説と違っても、問いと判定基準は書き換えない。** 「仮説は棄却された」と書く。**棄却は成果である。**
- 途中で問い自体が変わった場合は、そのファイルを `中断` にして新しいファイルを起こす。

> **`計画確定` の時点でレビューを受けること。**
> 「判定基準を結果を見てから変えない」は自己申告では守られない。
> 結果が出る前にレビューが入る運用にして初めて機能する（[QUALITY_BAR.md](../QUALITY_BAR.md)）。

## ステータス

ファイル冒頭に必ず記載する。

| ステータス | 意味 |
|---|---|
| `計画中` | 計画を執筆中。判定基準が未確定。参照対象外 |
| `計画確定` | 計画が固まった。集計未着手 |
| `検証中` | 集計・検証を実行中。結果は暫定であり、資料に転記しない |
| `完了` | 結果と解釈まで記載済み。参照可 |
| `中断` | 前提の崩壊・データ不足などで打ち切り（理由と、後継ファイルがあればリンクを記載） |

**`検証中` までの数値を報告資料に転記しない。** 暫定値が独り歩きすると出所を追えなくなる。

## 置くもの

- 分析計画とその結果（同一ファイル、Markdown）
- その分析が生んだ図と集計値（分析IDのフォルダ配下）

## 置かないもの

- 個人情報・顧客識別情報を含む生データ → [data/](../../data/) で管理し、パスと取得方法のみ記載
- 再現用スクリプト → [scripts/](../../scripts/)（分析IDと1対1）
- 複数の分析で使う共通処理 → [src/](../../src/)
- 探索・試行錯誤の途中経過 → [notebooks/](../../notebooks/)（Git管理外。結果として扱う段階で `scripts/` に書き直す）
- 変数定義・データ形状・基本統計量 → [data-dictionary/](../data-dictionary/)
- 施策の提案そのもの → [ideas/](../ideas/)
- 事業構造や業務フローの説明 → [business/](../business/)

## 命名規則：分析者ごとのディレクトリ

**分析は担当者ごとのディレクトリに分ける。** 複数人が同時に分析する運用では、共有の連番台帳を都度確認して採番するコストが高く、衝突・上書きの原因になる。担当者内で完結する連番にすることでこれを避ける。

```
docs/analysis/<担当者名>/ANL-NNN_<分析テーマ>.md     例: docs/analysis/hirose/ANL-003_aging_by_contract_type.md
docs/analysis/<担当者名>/ANL-NNN_<分析テーマ>/        図・集計値の置き場（本体の .md と同名）
```

- `<担当者名>` はローマ字の姓など、チーム内で一意に判別できる短い識別子。
- `NNN` は**担当者ディレクトリ内で**連番。他の担当者の採番とは独立でよい（衝突しない）。採番済みの番号は再利用しない。
- 分析IDそのものは `ANL-NNN`（担当者名を含まない）。案件横断で引用するときは `hirose/ANL-003` のように担当者ディレクトリ名を添えて曖昧さをなくす。
- **計画を書いた時点で採番する。** 日付を名前に使わないのは、計画日と実施日が離れるため。日付は本文の「起案日／最終更新日」で管理する。

新規に始めるときは [_TEMPLATE.md](_TEMPLATE.md) を自分のディレクトリにコピーして採番する。自分のディレクトリがなければ作成する。

## 成果物（図・集計値）の保管

分析が増えても追えなくなる原因は、**どの数値がどの分析のどの手順から出たか分からなくなること**。それを防ぐための構成。

### ディレクトリ構成

```
docs/analysis/
├── README.md
├── _TEMPLATE.md                          新規分析のひな形
├── _archive/                             中断・更新版が出た分析の退避先
├── <担当者A>/
│   ├── ANL-001_<テーマ>.md               入口。1分析＝必ずこの .md 1枚から辿れる
│   └── ANL-001_<テーマ>/                 成果物。.md と同名フォルダ
│       ├── figures/
│       │   └── fig01_<内容>.png
│       └── tables/
│           └── tbl01_<内容>.csv
└── <担当者B>/
    └── ANL-001_<テーマ>.md               担当者ごとに ANL-001 から始まってよい

scripts/<担当者名>/ANL-001_<テーマ>.py    再現スクリプト（分析IDと1対1。scriptsも担当者別に分ける）
src/                                       複数分析で使う共通処理（ローダ・正規化・集計関数）
notebooks/<担当者名>/                       探索用の作業場。Git管理外（[notebooks/README.md](../../notebooks/README.md)）
data/                                       入力データ。Git管理外（[data/README.md](../../data/README.md)）
```

図・集計値が1点もない分析はフォルダを作らない。`.md` だけで完結させる。

### ファイル命名

```
fig01_<内容>.png     図。連番は .md 本文に登場する順
tbl01_<内容>.csv     集計値。連番は .md 本文に登場する順
```

- 連番は**分析内で通し**。`fig01` と `tbl01` は別系統でよい。
- 番号は再利用しない。差し替えたら旧番号は欠番のままにする（資料側の参照が指す先を変えないため）。
- `final` `修正版` `v2` `new` を名前に付けない。作り直しが必要なら新しい分析IDを起こす。

### 保管ルール

1. **`.md` から参照されていない図・集計値は置かない。** 使わなくなったら消す。フォルダに残った出所不明のファイルが、後から「これは何の数字か」を潰す。
2. **`.md` に「図表・集計値一覧」を必ず書く。** ファイル名・内容・生成元（スクリプトのどの処理か）を表で持ち、フォルダの中身が常に本文から索引される状態にする。
3. **図には必ず対応する集計値を残す。** グラフだけあって元の数値がない状態を作らない。図の元データは `tables/` に同じ内容で置く。
4. **Gitに入れるのは「資料に載せる粒度」まで。** 目安は1ファイル1000行・1MB未満。それを超える中間データは `data/processed/` に置き、`.md` にはパスと生成方法だけ書く。
5. **個人・個体を特定できる列を含むファイルは置かない。** 氏名・住所・電話番号・個別の識別番号を列に持つCSVは、集計途中であっても `docs/` 配下に置かない。
6. **形式を揃える。** 図は PNG（幅1200px以上）、集計値は CSV（UTF-8 BOM付き・カンマ区切り・日付は `YYYY-MM-DD`）。表計算ソフトで開く前提のためBOMを付ける。
7. **`検証中` の作業ファイルは `完了` 時に片づける。** 試行錯誤の途中生成物は消す。残す場合は理由を `.md` に書く。

### アーカイブ

`中断` になった分析、および更新版が出て参照されなくなった分析は、`.md` とフォルダを**セットで** [_archive/](_archive/) に移す。

- 削除はしない。過去の判断が何を根拠にしていたかを追えなくしないため。
- [INDEX.md](../INDEX.md) の行は消さず、リンク先を `_archive/` 配下に張り替え、ステータスと後継ファイルを明記する。
- `_archive/` の中身は参照禁止ではないが、**資料への新規転記は不可**。

## 各ファイルの必須記載事項

以下は省略しない。特に **前提** と **データソース** は必須。**前提が書かれていない分析は参照禁止とする。**
`【計画】` は①で埋める欄、`【結果】` は④で埋める欄。計画段階では `【結果】` 側を見出しだけ残して空にしておく。

構成の実体は [_TEMPLATE.md](_TEMPLATE.md) を参照（コピーして使う）。

### サマリー（400字以内）

ファイル冒頭、ステータスのすぐ下に置く。**結論だけを400字以内で書く。** 前提・手法・数値の細部は書かない。
狙いは、他のファイルやAIがこの分析を参照するときに全文を読まずに要点を掴めるようにすること（コンテキスト効率）。

- `計画中` `計画確定` `検証中` の段階では「（未着手／検証中のため未記載）」とだけ書く。**暫定の結論を書かない。**
- `完了` になった時点で、判定基準に照らした結論のみを400字以内で書く。**言えないことがあれば1文で触れる。**
- `中断` の場合は中断理由を短く書く。
- 詳細は本文の「解釈」「この分析で言えないこと」に譲る。サマリーと本文で結論が食い違ってはならない。

| 節 | 段階 | 要点 |
|---|---|---|
| 問い | 計画 | 1文。「〜は〜か」の形 |
| 仮説 | 計画 | 作業仮説。棄却されても問題ない前提で書く。なければ「なし（探索的）」 |
| データソース | 計画 | 出所・対象期間・レコード件数・関連する定義 |
| 前提・制約 | 計画 | 除外するデータと理由／補完・推定する箇所／**崩れたら結論が変わる点** |
| 手法 | 計画 | 使う列、結合キー、集計単位まで |
| **判定基準** | 計画 | **結果を見る前に決める。** 何がどう出たら何が言えるのか |
| 未確認事項 | 計画 | 集計前に潰すべき論点。なければ「なし（確認済み）」 |
| 実行記録 | 結果 | 実行日・実行者・再現スクリプト・入力データの実ファイル名 |
| 計画との差異 | 結果 | 計画どおりに実行できなかった点と理由。なければ「なし」 |
| 結果 | 結果 | 数値と図表。**解釈は書かない** |
| 図表・集計値一覧 | 結果 | フォルダ配下のファイルはすべて載せる |
| 解釈 | 結果 | 判定基準に照らして言えることのみ |
| この分析で言えないこと | 結果 | **空欄にしない** |

### 判定基準の書き方

「結果を見る前に、何がどう出たら何が言えるのか」を書き切る。**ここが分析の質を決める。**

```markdown
## 判定基準 【計画】
- 契約種別ごとの90日超延滞率の差が 10pt 以上 → 「種別による差がある」と扱う
- 10pt 未満 → 「差はない」と扱い、種別を軸にした施策は候補から外す
- 順位が仮説と逆順で一致した場合 → 仮説を棄却し、逆方向の要因を次の分析で立てる
```

- 定量的に線を引けない場合は「**線を引けない（記述に留める）**」と明記する。それも判定基準である。
- **判定基準が書けない問いは、まだ問いになっていない。** 問いの立て直しに戻る。

## 運用ルール

1. **判定基準は結果を見た後に変えない。** どうしても変える必要が出た場合は、旧基準を消さず「更新履歴」に旧基準・変更理由・変更日を残す。
2. **前提が変わったら書き換えず、新しいファイルを作る。** 旧ファイルの冒頭に `> 更新版: <新ファイルへのリンク>` を追記する。過去の判断が何を根拠にしていたかを追えなくしない。
3. **数値には必ず出所を添える。** 出所のない数値は資料に転記しない。
4. **推定値・仮定値は明示する。** 実測値と同じ書式で並べない（`※推定` を付す）。
5. **再現できる形で残す。** 手作業で集計した場合は、その手順を「手法」に書く。**再実行できない集計は結果として扱わない。**
6. 新規作成・ステータス変更したら [INDEX.md](../INDEX.md) に反映する。
