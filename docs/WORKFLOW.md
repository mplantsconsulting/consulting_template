# WORKFLOW — 提案までの7ステップ

依頼を受けてから提案を出すまでの標準の順序。**フォルダ構成と1対1に対応させてある**ので、
「どこに何を置くか」を毎回考えなくてよい。

```
依頼
 │
 ├─ Step 0  依頼を問いに変える          → CLAUDE.md
 │
 ├─ Step 1  業務と市場を理解する        → docs/business/  docs/cases/
 │
 ├─ Step 2  用語とデータを定義する      → docs/data-dictionary/
 │
 ├─ Step 3  問題を構造化する            → docs/strategy/
 │
 ├─ Step 4  問いを分析に落として検証    → docs/analysis/ + scripts/ + src/
 │
 ├─ Step 5  施策を起案する              → docs/ideas/
 │
 ├─ Step 6  意思決定者に提示する        → docs/presentations/
 │
 └─ Step 7  決着しないことを確認事項に  → docs/client-qa/
                                            │
            回答が来たら Step1 / Step2 を更新して Step3 へ戻る ←┘
```

## 完了の判定

各ステップは「作業した」ではなく**以下の状態になったとき**に完了とする。

| Step | やること | 完了の判定 |
|---|---|---|
| 0 | 誰の、どの意思決定を動かすのかを1文で書く。KGIと役割・禁止事項を `CLAUDE.md` に固定 | KGIが1文で書けている |
| 1 | 一次資料から業務フローを図にする。外部事例を出典付きで調べる | フローの各段階に「未確認」タグが付いた状態で図になっている |
| 2 | 変数定義・データ形状・結合キー・欠損を台帳化。**指標の定義を1ファイルに集約** | 「この語はこの定義」が1箇所で決まっている |
| 3 | 問題をMECEに割り、各枝に事実・数値を貼る。**空欄を残す** | 空欄の一覧が次のアクションになっている |
| 4 | 計画（判定基準まで）→ 集計 → 結果・解釈。1ファイル＝1つの問い | ステータスが `完了`、かつ「言えないこと」が書かれている |
| 5 | 施策1件＝1ファイル。効果は条件付きで書く。見送りも残す | 未確認事項が空欄でない |
| 6 | `sources.md` に全数値の出所を書く。載せるのは `完了` の数値だけ | 質疑で `sources.md` だけを見れば根拠に辿れる |
| 7 | データでは決着しない論点を、答えやすい形（選択肢・単語1つ）で照会 | 各質問に「分からない」の選択肢がある |

## 必ず守ること

### 1. Step 1・2 を飛ばして Step 4 に行かない

**これが最も多い失敗である。**
データはすぐ触れるが、業務は聞かないと分からない。
**触れるものから始めると、業務の理解が永久に後回しになる。**

> **データは業務の影である。** 業務を知らずにデータを見ると、影の形だけを議論することになる。

意味の分からない列は、業務を知らないままでは分析に使えない。
値の分布を眺めても、その列が業務のどの工程で誰によって入力されたのかは分からない。

### 2. 最初の1〜2週間が Step 1・2 で終わるのは正常

コードを書いていない期間があることを不安に思わなくてよい。
むしろ**この期間に手を動かしてしまうことが、後の全部を無駄にする。**

### 3. 一方通行ではなくループ

Step 7 の回答が来たら Step 1・2 を更新し、影響する分析（Step 4）を見直す。
1周目の結論は暫定である。

### 4. Step 7 は成果物である

「分からなかったこと」を答えやすい形で持ち帰らせるのは、**コンサルタントの仕事の一部**であって手抜きではない。
確認事項のない提案は、確認していないだけである。

### 5. 提示物に載せてよいのは、上流が確定しているものだけ

| 載せるもの | 条件 |
|---|---|
| 数値 | `docs/analysis/` のステータスが `完了` |
| 事実記述 | `docs/business/` で `【仮説・未確認】` が外れている |
| 施策 | `docs/ideas/` のステータスが `検討中` 以上 |

`検証中` の数値を資料に転記しない。**暫定値は必ず独り歩きする。**

## 各ステップの思考の型

Step ごとに使う「型」を4つに絞ってある。フレームワークの暗記ではなく**手続き**として使う。

### ① 問いを立てる（Step 0・4 の入口）

依頼文は問いではない。

**手続き**: 論点を書く → 問いを1文（「〜は〜か」）で書く → **判定基準を先に書く**

- **判定基準が書けない問いは、まだ問いになっていない。**
- 定量的に線が引けない場合は「**線を引けない（記述に留める）**」と明記する。それも判定基準である。
- 判定基準の例:
  > 「契約種別ごとの90日超延滞率の差が◯pt以上なら、種別による差があると見なす。◯pt未満なら差はないものとして扱う」

  **ここまで書いてから集計する。** この文章があると、どんな数字が出ても解釈が動かない。

### ② 構造化する（Step 3）

深掘りの前に全体を割る。割らずに深掘ると **調べたところだけが問題に見える。**

**手続き**: 全体を定義 → ダブりなくモレなく割る → 各枝に数字・事実を貼る → **空白の枝を「未確認」として残す**

- **構造化の価値は「埋まった枝」ではなく「空欄が見えること」。**
- 「算出不可」「データなし」のセルの一覧が、そのまま次の分析計画と確認事項になる。

### ③ 仮説を持って検証する（Step 4）

全部調べるのは不可能。仮説を立てて当たり外れを高速に判定する。

**手続き**: 仮説を書く → 判定基準を書く → 検証 → 棄却されたら「棄却された」と書く（**問いと判定基準は書き換えない**）

- **棄却は成果である。** 打ち手の候補が減ることは、提案の質が上がることと同じ。
- 「効果が見込めないと確認できたもの」は、資料に載せるべき価値のある結果である。

### ④ 現場から考える（Step 1）

**手続き**: 一次資料（契約書・約款・規程）→ 業務フローを図に → ヒアリングで実態確認 → **その後にデータ**

- **規程は「できること・義務」であって「やっていること」ではない。**
  規程に書かれた条項が実際に運用されているかは、必ず別に確認する。
- 過去の社内成果物・手順書・コードが読めることは、**それが稼働していることの証明にならない。**

## Step 6（提示）の設計

資料は「分析の報告」ではなく「相手が判断するための道具」である。

- **見出しは結果を述べる文にする。** 解釈を含む言い切りにはしない。
- **数字はそのページで示す結果だけ。** 網羅性は Appendix に落とす。
- **スライドに載せる内容と、口頭で補足する内容を構成段階で分ける。**
  仮説・解釈・留保は口頭で説明し、スライドには分析の内容と結果を置く、という切り分けが基本。
- **棄却した仮説を隠さない。** サマリページに「効果が見込めないと確認できたもの」の欄を置く。
- **留保（母集団のカバー率、抽出条件の未確認など）は口頭で必ず伝える。** 構成案に宿題として明記する。

詳細は [presentations/README.md](presentations/README.md)。

## AIの使い方

Step のどこでも使うが、**やらせないこと**を先に決めてある。

| | やらせない | なぜ |
|---|---|---|
| 1 | **判断させる** | AIは根拠の強さに関わらず「Aが良いです」と必ず言う。採否・優先順位は人が決める |
| 2 | **出典・数値を生成させる** | URLも統計値も捏造される。「確認できなかった」と書かせる運用にする |
| 3 | **前提の穴を埋めさせる** | 最も危険。もっともらしい一般論が事実として下流に流れる |

**判断が鈍らないための運用ルール**

1. **AIに聞く前に、自分の答えを1行書く。** 差分が学習になる。書けないなら、まだ問いが立っていない。
2. **AIの結論を、自分の言葉で一度否定してみる。** 否定できなかった理由が、そのまま自分の根拠になる。
3. **禁止事項は口で言わず [CLAUDE.md](../CLAUDE.md) に固定する。**

用意してあるスキル・コマンドは [.claude/README.md](../.claude/README.md)。

## gitの使い方

| # | ルール | なぜ |
|---|---|---|
| 1 | **ドキュメントをコードと同じリポジトリに置く** | 数値・スクリプト・解釈が一緒にバージョン管理される。チャットと表計算ソフトに散ると「どれが最新か」が分からなくなる |
| 2 | **上書きしない。** 前提が変わったら新ファイル＋後継リンク | 過去の判断の根拠を消さない |
| 3 | **コミットは検証の単位。** ファイル単位でまとめない | 例: `ANL-012 完了` / `business: 規程から猶予日数を確定` |
| 4 | **`INDEX.md` を更新する** | 索引のないドキュメント群は、増えた瞬間に誰も読まなくなる |
| 5 | **ステータスを冒頭に書く** | 読み手が「参照していいか」を自分で判断できる |
