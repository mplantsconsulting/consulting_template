# cases — 他社事例・外部ソリューション調査

## 目的

検討材料として、**社外の一次情報（プレスリリース・IR・業界メディア・学術論文・ベンダー公式ケーススタディ等）**に基づき、
同業他社・他業種・スタートアップ/SaaS の取り組み事例を収集・整理する。

**ここに置く情報はクライアントの事実ではなく、あくまで外部の参考事例である。**
[strategy/](../strategy/) や [ideas/](../ideas/) の根拠として直接引用してよいのは
「〇〇社ではこういう施策が存在する（出典あり）」という**事実そのものまで**であり、
**「だからクライアントでも効果が出る」という因果は本フォルダの記述だけでは立証されない。**

## 置くもの

- 同業他社（類似のビジネスモデル・業務構造を持つ事業者）の取り組み事例
- 他業種の先進事例（構造が似ていれば業種は問わない）
- 関連するソリューションを提供するスタートアップ・SaaS の実在するプロダクト
- 各事例の出典（URL・記事タイトル・日付）

## 置かないもの

- クライアント自身の事実・データ → [business/](../business/) [data-dictionary/](../data-dictionary/) [analysis/](../analysis/)
- 収集した事例をもとにした施策の採否判断・具体的な実行案 → [ideas/](../ideas/)（本フォルダの事例を根拠としてリンクする）
- 収集した事例をもとにした戦略レベルの論点整理 → [strategy/](../strategy/)

## 命名規則

```
CASE-NNN_<テーマ>.md    例: CASE-001_same_industry_practices.md
```

`NNN` は連番。採番済みの番号は再利用しない。雛形: [_TEMPLATE.md](_TEMPLATE.md)

## サマリー（400字以内）

ファイル冒頭、調査対象範囲のすぐ下に置く。**この調査から言える結論・示唆の要点のみを400字以内で書く。** 事例の詳細・出典は書かない。
狙いは、他のファイルやAIがこの調査を参照するときに全文を読まずに要点を掴めるようにすること（コンテキスト効率）。

- 「情報が確認できなかった項目」が多い場合は、その旨を1文で触れる。
- 反例・限界が報告されている場合は、それも踏まえた結論にする（都合のよい事例だけを要約しない）。
- 詳細は本文の「事例一覧」「示唆」に譲る。サマリーと本文で結論が食い違ってはならない。

## 出典の扱いに関する注意（重要）

**この節が本フォルダの本体である。** AIに調査を任せる場合、特にここが守られているかを確認する。

1. **推測で埋めない。** 検索で確認できなかった事項は「情報不足」「非公開」と明記し、埋め合わせで一般論を書かない。
2. **出典URLは実在するものだけを書く。** **記憶からの捏造は禁止。** 裏取りできなかった数値には出典欄で「要検証」等の留保を明記する。
3. **数値の性質を区別する。** 以下のどれに当たるかを各事例に明記する。

   | 種別 | 信頼度の扱い |
   |---|---|
   | 独立検証がある学術論文・規制当局資料の数値 | 最も強い |
   | 企業のIR・プレスリリースの数値 | 一次情報だが**自社発表** |
   | ベンダー（SaaS提供企業）公表の導入効果 | **マーケティング目的の可能性がある自己申告値** |

4. **反証・限界も記録する。** 「効果があった」事例だけでなく、
   「見かけ上の改善に留まった」「規制対応が後手に回った」等の反例も、判断材料として**同格に扱う。**

## 運用ルール

1. 新規作成したら [INDEX.md](../INDEX.md) に反映する。
2. 同じテーマを再調査した場合は上書きせず新しいファイルを起こし、旧ファイルの冒頭に後継リンクを追記する。
3. ここから [ideas/](../ideas/) へ引用する際は、**「CASE-NNN のどの事例」かを明示してリンクする。**
