# strategy — 問題整理・戦略レイヤー

## 目的

案件の課題を、[business/](../business/)（事実）と [analysis/](../analysis/)（数値）を土台に、
**戦略レベルの抽象的なレイヤーで整理する。**
個別施策そのものではなく、「どこに問題があり、どう構造化して捉えるか」という論点整理・フレームワークを置く。

**ここでの議論は、前提や参照した分析の内容によって変わりうる。**
結論を固定的な事実として扱わず、依拠した前提が崩れたら書き換えず新しいファイルを起こす
（[analysis/README.md](../analysis/README.md) と同じ運用）。

## 構造化のやり方

深掘りの前に全体を割る。**割らずに深掘ると、調べたところだけが問題に見える。**

```
① 全体を定義する      何の総量を割るのかを1文で書く
        ↓
② ダブりなくモレなく割る   MECE。割り方の軸を明記する
        ↓
③ 各枝に数字・事実を貼る   出所（analysis / business）を必ずリンクする
        ↓
④ 空白の枝を「未確認」として残す   ← ここが成果物
```

> **構造化の価値は「埋まった枝」ではなく「空欄が見えること」。**

「算出不可」「データなし」のセルの一覧が、そのまま
**次の分析計画（[analysis/](../analysis/)）とクライアントへの確認事項（[client-qa/](../client-qa/)）になる。**
空欄を無理に埋めない。埋めたら、それは推測である。

## 置くもの

- 問題の構造化（イシューツリー、論点の切り分け、仮説の全体像、損失・機会の因数分解など）
- 複数の分析結果・事実を束ねた戦略レベルの示唆
- 施策を検討する前段としての優先順位づけ・フレームワーク

## 置かないもの

- 個別の施策案そのもの → [ideas/](../ideas/)（ここでの整理を根拠としてリンクする）
- 数値分析の計画・実行・結果そのもの → [analysis/](../analysis/)（ここでは結果を引用するのみ）
- 事業構造・業務フローの事実 → [business/](../business/)
- 意思決定者への提示資料 → [presentations/](../presentations/)

## 命名規則

```
STR-NNN_<テーマ>.md    例: STR-001_issue_tree.md
```

`NNN` は連番。採番済みの番号は再利用しない。雛形: [_TEMPLATE.md](_TEMPLATE.md)

## ステータス

ファイル冒頭に必ず記載する。

| ステータス | 意味 |
|---|---|
| `draft` | 書きかけ。他者の参照対象外 |
| `検討中` | 論点整理を進めている段階 |
| `確定` | 現時点の前提のもとで整理が固まった。参照可 |
| `更新版あり` | 前提が変わり後継ファイルに移行済み（後継へのリンク必須） |

## 運用ルール

1. **推測で埋めない。** 依拠する事実・数値には出所（`business/` `analysis/` のファイル）を必ず添える。
2. **前提が変わったら書き換えず、新しいファイルを作る。** 旧ファイルの冒頭に `> 更新版: <新ファイルへのリンク>` を追記し、ステータスを `更新版あり` にする。
3. **施策の採否はここで判断しない。** ここは論点整理までとし、具体的な施策案は [ideas/](../ideas/) に切り出す。
4. **示唆は断定しない。** 「前提の上でここまでは言える」という範囲を明記する。
5. 新規作成・ステータス変更したら [INDEX.md](../INDEX.md) に反映する。
