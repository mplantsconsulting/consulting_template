# presentations — 提出・報告資料

## 目的

クライアントおよび社内に提出する資料を管理する。
**このフォルダの内容は対外的に出る。** 他フォルダより検証のハードルを一段上げる。

## 置くもの

- 報告会・提案の資料（Markdown 原稿、pptx / xlsx 等の成果物）
- 資料に付随する配布物（Appendix、数値の裏付け表）

## 置かないもの

- 未確定情報、検討途中のメモ → [ideas/](../ideas/) または [analysis/](../analysis/)

## 命名規則

```
YYYYMMDD_<提出先>_<件名>/          1回の提出につき1フォルダ
  ├── outline.md                   構成・メッセージライン（先に作る）
  ├── <資料本体>.pptx
  ├── sources.md                   数値・主張の出所一覧（必須）
  └── feedback.md                  提出後に作る。反応・宿題・次アクション
```

日付は提出日（予定日で作成し、確定後にリネームしない — 実提出日が変わった場合は `sources.md` に追記）。
構成の雛形: [_TEMPLATE_outline.md](_TEMPLATE_outline.md)

---

## 掲載の条件

資料に載せてよいのは、以下を満たすものだけ。

1. **数値**は [analysis/](../analysis/) のステータス `完了` のファイルに紐づいている
   （`sources.md` にファイル名と該当箇所を記載）
2. **事実記述**は [business/](../business/) で `【仮説・未確認】` が外れている
3. **施策**の記述は [ideas/](../ideas/) のステータスが `検討中` 以上

推定値・シミュレーション値を載せる場合は、**スライド上に前提を明記する。前提を書けないなら載せない。**

## 資料の設計方針

資料は「分析の報告」ではなく **「相手が判断するための道具」** である。

### スライドに載せるものと、口頭で補足するものを構成段階で分ける

`outline.md` の各ページを **`スライドに載せる`** と **`口頭で補足`** の2段に分けて書く。

| どこに | 何を |
|---|---|
| **スライド** | 分析の内容と結果 |
| **口頭** | 仮説・解釈・示唆・留保・判断のお願い |

この切り分けをすると、スライドから解釈が消えて事実だけが残る。
**質疑で崩れるのは、たいていスライドに書いた解釈のほうである。**

### そのほかの原則

- **見出しは結果を述べる文にする。** 解釈を含む言い切りにはしない。
- **数字はそのページで示す結果だけ。** 網羅性は Appendix に落とす。
- **棄却した仮説を隠さない。** サマリページに「**効果が見込めないと確認できたもの**」の欄を置く。
  「調べたが効果がなさそうと分かった」は、相手の意思決定を確実に助ける結果である。
- **留保を口頭で必ず伝える宿題として構成案に明記する。**
  母集団のカバー率、抽出条件の未確認、対照群の不在などは、言い忘れると後で問題になる。
- **判断してほしいことを明確にする。** ただしスライドに置くか口頭にするかは案件で判断する。

## 運用ルール

1. **版を上書きしない。** 提出済みの資料は編集せず、**新しい日付フォルダを作る。**
   何をいつ相手に伝えたかの記録が崩れる。
2. **`sources.md` を必ず作る。** 質疑で数値の根拠を聞かれた際に**ここだけを見れば辿れる**状態にする。
3. **提出後は結果を残す。** 同フォルダに `feedback.md` を作り、先方の反応・宿題・次アクションを記録する。
   宿題は [client-qa/](../client-qa/) または [analysis/](../analysis/) に落とす。
4. **提出前に [QUALITY_BAR.md](../QUALITY_BAR.md) のチェックリストを通す。** ペアで相互チェックする。
5. 新規作成したら [INDEX.md](../INDEX.md) に登録する。
