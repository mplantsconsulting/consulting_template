# assumption-audit — 前提を洗い出して格付けする

## いつ使うか

- 施策や結論を資料に載せる前（WORKFLOW の Step 5・6 の手前）
- 「もっともらしいが、何かが引っかかる」とき
- **AIが出した結論を採用する前**（前提の穴を一般論で埋められていないかの検出）
- 分析の計画時（`docs/analysis/` の「前提・制約」を埋める前）

## 前提

**危ないのは「間違っている前提」ではなく、「誰も確かめていない前提」である。**
間違いは指摘されるが、確かめられていない前提は**そのまま下流に流れる。**

特に以下は、書いた本人も前提だと気づいていないことが多い。

- **暗黙の前提** — 明示されていないが、崩れると結論が変わるもの
- **データの前提** — 母数・抽出条件・対象期間・カバー率
- **業務の前提** — 「規程にあるから運用されているはず」「手順書にあるから現場に存在するはず」
- **一般論由来の前提** — 「普通はこうなっているはず」（**AIが埋めたものはここに集中する**）

## 進め方

1. **監査の対象を1つに絞る。** 結論・施策・分析のいずれか1つ。複数を混ぜない。
2. **前提を洗い出す。** 明示されているものと、**明示されていないもの**の両方。
   - 「この主張が成り立つために、何が真でなければならないか」を問う
   - **暗黙の前提を落とさない。** ここが監査の本体である
3. **前提を分類する。** データ / 業務 / 市場・外部 / 実行体制 / 経済性
4. **2軸で格付けする。**

   | 軸 | 見方 |
   |---|---|
   | **重要度** | この前提が崩れると結論はどうなるか（`結論が覆る` / `一部修正` / `影響なし`） |
   | **根拠の強さ** | 何に基づいているか（下表） |

   **根拠の強さの判定基準**

   | 強さ | 何に基づくか |
   |---|---|
   | **強** | 一次資料（契約書・約款・規程）、または `完了` の定量分析 |
   | **中** | ヒアリングで確認が取れた事実（回答日・回答者が記録されている） |
   | **弱** | 二次資料（抽出条件が未確認のデータ）、口頭の伝聞 |
   | **なし** | 三次資料のみ、業界の一般論、**推測**、AIが埋めた記述 |

5. **「重要度が高く、根拠が弱い」前提を特定する。**
   **これが本丸である。** ここだけを次工程に送る。
6. **それぞれを検証タスクに変換する。**

   | 変換先 | 条件 |
   |---|---|
   | [analysis/](../../../docs/analysis/) | 手元のデータで検証できる |
   | [client-qa/](../../../docs/client-qa/) | 聞けば答えが得られる |
   | [business/](../../../docs/business/) | 一次資料を読めば確定する |
   | **潰せない** | 検証手段がない。**そのことを明記して前提のまま進む** |

7. **判定を出す。** ただし**採否は判断しない。**
   「この前提を潰さずに出すと、どこで崩れるか」までを示す。

## 出力形式

```markdown
## 監査の対象
〈結論・施策・分析を1つ。原文を引用する〉

## 前提の一覧

| # | 前提 | 明示/暗黙 | 分類 | 重要度 | 根拠の強さ | 根拠 |
|---|---|---|---|---|---|---|
| 1 | | 暗黙 | データ | 結論が覆る | **なし** | 〈何に基づくか。なければ「推測」〉 |

## 要対応（重要度が高く、根拠が弱いもの）

**これが本丸。ここを潰さずに提出しない。**

| # | 前提 | 崩れたらどうなるか | 検証方法 | 変換先 |
|---|---|---|---|---|
| 1 | | | | → analysis / → client-qa / → business |

## 潰せない前提（検証手段がない）
〈前提のまま進む場合、資料・口頭でどう断るかを書く〉

## 根拠が「なし」だった前提
〈一般論・推測・AIが埋めた記述に由来するもの。**特に注意して報告する**〉

## 監査の結果
〈「この前提群のもとでは、ここまでは言える」という範囲。
  採否は判断しない〉
```

## 品質基準

- **暗黙の前提が1つ以上挙がっている**（明示されたものだけを並べていない）
- **根拠の強さが「何に基づくか」まで書かれている**（「弱」だけで終わっていない）
- **重要度が「崩れたら結論がどうなるか」で判定されている**（なんとなくの高中低にしていない）
- **要対応の各項目に、具体的な変換先がある**（「要検証」で終わっていない）
- **潰せない前提を「潰せない」と書いている**（無理に検証タスク化していない）
- 施策の採否を判断していない
- **監査する側が推測で前提を補っていない**（監査自体が同じ基準で評価される）
