# issue-structuring — 問題を構造化する

## いつ使うか

- 深掘りを始める前（WORKFLOW の Step 3）
- 分析結果が複数溜まり、全体像が見えなくなったとき
- 「どこから手を付けるべきか」を決めるとき

## 前提

深掘りの前に全体を割る。**割らずに深掘ると、調べたところだけが問題に見える。**

> **構造化の価値は「埋まった枝」ではなく「空欄が見えること」。**

**空欄を無理に埋めない。埋めたら、それは推測である。**
「算出不可」「データなし」のセルの一覧こそが、次の分析計画と確認事項になる。

## 手順

1. **何の総量を割るのかを1文で書く。** これが定義できないなら構造化に入らない。
2. **割り方の軸を明記する。** 軸は1つに絞る。複数の軸を混ぜるとMECEが崩れる。
   - 軸の候補を2〜3案出し、**どの軸で割ると意思決定に近いか**で選ぶ
3. **ダブりなくモレなく割る。** 各階層で以下を確認する。
   - 足すと全体に戻るか（モレがないか）
   - 同じものが2つの枝に入っていないか（ダブりがないか）
   - 「その他」が最大の枝になっていないか（**なっていたら軸が間違っている**）
4. **各枝に数字・事実を貼る。** 必ず出所をリンクする。
   [analysis/](../../../docs/analysis/) の `完了` のもの、または [business/](../../../docs/business/) の一次資料のみ。
5. **埋まらない枝を明示する。** 以下を区別する。

   | 表記 | 意味 |
   |---|---|
   | `算出不可` | データはあるが、定義・母数が確定せず計算できない |
   | `データなし` | そもそもデータが存在しない／受領していない |
   | `未検証` | 計算できるが、まだやっていない |
   | `業務不明` | 業務の実態が分からず、数字の意味が確定しない |

6. **空欄の一覧を作り、次のアクションに変換する。**
   → [analysis/](../../../docs/analysis/) で検証 / → [client-qa/](../../../docs/client-qa/) で照会 / → データ追加依頼

## 出力形式

[docs/strategy/_TEMPLATE.md](../../../docs/strategy/_TEMPLATE.md) に沿って書く。要点は以下。

```markdown
## 割る対象
〈何の総量を割るのか。1文〉

## 割り方の軸
〈軸を1つ明記する。なぜこの軸を選んだかを1文で〉

検討した他の軸: 〈採らなかった軸と理由〉

## 構造

| # | 枝 | 内容 | 数値 | 出所 |
|---|---|---|---|---|
| ① | | | | [ANL-NNN](...) |
| ② | | | `算出不可` | 理由: |

（階層が深い場合はツリーまたはMermaidで示す）

## 空欄の一覧（このファイルの主な成果物）

| # | 空欄の枝 | 区分 | なぜ埋まらないか | 次のアクション |
|---|---|---|---|---|
| 1 | | 算出不可/データなし/未検証/業務不明 | | → analysis / → client-qa |

## 示唆
〈前提の上でここまでは言える、という範囲。断定しない〉

## この整理で言えないこと
〈空欄にしない〉
```

## 品質基準

- **「その他」が最大の枝になっていない**（なっていたら軸を作り直す）
- **各枝の数値に出所リンクがある**（ないものは空欄として扱う）
- **空欄の一覧が、そのまま次のアクションになっている**
- 施策の採否をここで判断していない（[ideas/](../../../docs/ideas/) の仕事）
- 空欄を一般論・推測で埋めていない
