# business-understanding — 業務を理解する

## いつ使うか

- 案件の最初（WORKFLOW の Step 1）
- **データを触る前。** 分析の前提が業務理解に依存すると気づいたとき
- 意味の分からない列が出てきたとき

## 前提

> **データは業務の影である。** 業務を知らずにデータを見ると、影の形だけを議論することになる。

**規程・約款は「できること・義務」であって「やっていること」ではない。**
条項に書かれていても、実際にその運用が行われているかは別の事実である。

**過去の社内成果物・手順書・コードが読めることは、それが稼働していることの証明にならない。**

## 情報源の階層を必ず先に判定する

| 階層 | 何か | 扱い |
|---|---|---|
| **一次** | 契約書・約款・規程・重要事項説明書・公開IR・法令 | **正。** 事実として引用してよい |
| **二次** | クライアント提供の生データ | 列構成は事実、**母数・抽出条件は不明** |
| **三次** | 社内の手順書・マニュアル・過去の成果物・RPA/OCR等のコード | **業務フローの根拠にしない** |
| **参考** | 業界の標準形・一般論 | **事実ではない。** ヒアリング項目の下敷きにのみ使う |

**三次資料から読み取った内容は「業務がこうである」ではなく
「〈誰か〉がこう作った／こう理解していた」としてのみ記録する。**

## 手順

1. **手元の資料を階層に分類する。** 一次資料が手元にない場合、**そのことを明記して始める。**
   「一次資料が入手できていない」は記録すべき情報である。
2. **一次資料から業務の段階を列挙する。** 図にできる粒度まで分ける。
3. **各段階について以下を埋める。分からない欄は空にせず「未確認」と書く。**
   - 何が起きるか / 誰が行うか / いつ / 使うシステム・帳票
   - **データがどこに残るか**（[data-dictionary/](../../../docs/data-dictionary/) との接続点）
   - 根拠（情報源の階層とファイル名）
4. **未確認の記述に `【仮説・未確認】` を付け、確認方法と確認担当を併記する。**
5. **「規程にはあるが、実際に運用されているか未確認」の項目を別立てで洗い出す。**
   ここが後で事実誤認になりやすい。
6. **分かっていないことの一覧を作る。** → [client-qa/](../../../docs/client-qa/) の質問の元にする。

## 出力形式

[docs/business/_TEMPLATE_flow.md](../../../docs/business/_TEMPLATE_flow.md) に沿って書く。

加えて、ヒアリング項目を作る場合は以下。

```markdown
## ヒアリング項目

| # | 聞くこと | なぜ聞くか（これが分からないと何が言えないか） | 聞く相手 | 回答形式 |
|---|---|---|---|---|
| 1 | | | | 選択肢 / 単語1つ |

（「調べないと分からない」ものは質問にせず、データ追加依頼に分離する）
```

## 品質基準

- **各記述に情報源の階層が明記されている**
- **一次資料と三次資料の記述が混ざっていない**
- **「規程にある」と「実際に行われている」を書き分けている**
- **未確認の欄が空欄になっていない**（「未確認」と書く）
- **業界の一般論を、そのクライアントの事実として書いていない**
- 分からない列の意味を推測で埋めていない
