# issue-framing — 依頼を問いに変換する

## いつ使うか

- クライアントからの依頼文を受け取った直後（WORKFLOW の Step 0）
- 分析を始める前（Step 4 の入口）
- 「何を調べればいいか分からない」と言われたとき

## 前提

**依頼文は問いではない。** 「未収を減らしたい」「DXを進めたい」は依頼であって、
問いに変換する作業が最初の仕事である。

**判定基準が書けない問いは、まだ問いになっていない。**

## 手順

1. **依頼文をそのまま引用する。** 解釈を混ぜず、書かれていることだけを抜き出す。
2. **意思決定者と、動かしたい意思決定を特定する。**
   分からない場合は「不明」と書き、確認事項に回す。**推測で埋めない。**
3. **論点を列挙する。** 依頼を成立させるために答えが必要な問いを、粒度を揃えて並べる。
4. **各論点を「〜は〜か」の1文の問いに変換する。**
5. **各問いに判定基準を書く。** 何がどう出たら何が言えるのかを、**結果を見る前に**書き切る。
6. **判定基準が書けない問いを分類する。**

   | 書けない理由 | どうするか |
   |---|---|
   | 定量的に線を引けない | 「線を引けない（記述に留める）」と明記する。それも判定基準 |
   | データがない | [client-qa/](../../../docs/client-qa/) の照会項目にする |
   | 業務が分からない | [business/](../../../docs/business/) の確認項目にする。**分析にしない** |
   | 問いが大きすぎる | 分割する |

7. **優先順位を付ける。** 「この問いに答えると、どの判断が動くか」で並べる。
   **答えても判断が変わらない問いは落とす。**

## 出力形式

```markdown
## 依頼の内容（原文の要約）
〈依頼文に書かれていることだけ。解釈を混ぜない〉

## 意思決定者と、動かしたい意思決定
- 意思決定者:
- 動かしたい意思決定:
- 期限と提出形態:
（不明な項目は「不明 → 確認事項」と書く）

## 論点と問い

| # | 論点 | 問い（〜は〜か） | 判定基準 | 動く判断 | 優先度 |
|---|---|---|---|---|---|
| 1 | | | | | 高/中/低 |

## 判定基準が書けなかった問い

| # | 問い | 書けない理由 | 次のアクション |
|---|---|---|---|
| 1 | | データがない / 業務が不明 / 線が引けない | client-qa / business / 分割 |

## 落とした問い（答えても判断が変わらないもの）
〈落とした理由を書く。これも成果である〉

## この整理で決まっていないこと
〈空欄にしない〉
```

## 品質基準

- **判定基準のない問いを1つも残さない**（書けないものは理由付きで分類する）
- **「分析する」を問いにしない。** 「〜の傾向を分析する」は問いではない
- 意思決定者が特定できない場合、**推測で埋めずに「不明」と書く**
- 問いの数を絞る。**全部調べるのは不可能である**という前提で優先順位を付ける
- 出力先は [docs/analysis/](../../../docs/analysis/)（個別の問い）または
  [docs/strategy/](../../../docs/strategy/)（論点全体の整理）。テンプレートに沿って書く
