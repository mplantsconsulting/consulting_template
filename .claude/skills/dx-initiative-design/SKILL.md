# dx-initiative-design — DX施策を起案する

## いつ使うか

- 分析結果が揃い、施策の候補を書き出すとき（WORKFLOW の Step 5）
- 施策の実装工数を見積もる必要があるとき

## 前提（最重要）

**採否の決定はしない。** 判断材料を揃えるところまでが仕事である。
「Aが最も良いです」と言わない。**選択肢と、それぞれの前提・効果・コストを並べる。**

**起案の前に、根拠が次のいずれかであることを確かめる。**

- クライアントの一次資料（契約書・約款・規程）
- ヒアリングで確認が取れた事実
- 定量分析の結果（ステータス `完了`）

**三次資料（社内の手順書・過去の成果物・既存のコード）だけを根拠にした施策は起案しない。**
→ [client-qa/](../../../docs/client-qa/) の確認事項に回す。

> **コードが読めることは、それが稼働していることの証明にならない。**

## 我々の案件特性を踏まえた前提

我々は**実装を含む下流も担当する。**したがって施策は「提案」で終わらせず、以下とセットにする。

- **実装の有無と規模**（開発なしで済むものと、開発が必要なものを分ける）
- **工数の見立て**（前提を明記した上での概算）
- **効果の測定方法**（測れないなら「測れない」と書く）

## 手順

1. **施策を「開発なし」と「開発あり」の2群に分ける。**
   運用・基準・オペレーションの変更で済むものを先に洗い出す。
   **開発なしで効く施策は、実装を伴う施策より先に提示する価値がある。**
2. **各施策について、対象とする課題と根拠をリンクする。**
   根拠の種別（一次資料／ヒアリング／定量分析）を明記する。
3. **前提条件を洗い出す。** システム・法務・人員・他部署の合意・データの利用可否。
   各条件が `確認済` / `未確認` / `不足` のどれかを書く。
4. **期待効果を、言えることと言えないことに分ける。**
   - **効果を断定しない。** 「〜という前提が成り立てば〜」の形で書く
   - **根拠のない効果見込みの数値を書かない**
5. **コスト・リスク・副作用を書く。** 特に**副作用**（他の指標を悪化させる可能性、顧客体験への影響）を落とさない。
6. **実装が必要な場合、工数を見積もる。**

   | 項目 | 内容 |
   |---|---|
   | 必要な作業 | データ整備 / モデル開発 / 業務システム連携 / 画面 / 運用設計 |
   | 概算工数 | 人日。**前提（既存システムの状態など）を必ず併記** |
   | 前提が崩れた場合 | 工数がどう変わるか |

   **前提を書けない工数は書かない。**
7. **検証方法を書く。** 使う指標は
   [data-dictionary/](../../../docs/data-dictionary/) の定義台帳から**事前に1つ選ぶ**（複数を混ぜない）。
8. **未確認事項を空欄にしない。**

## 出力形式

[docs/ideas/_TEMPLATE.md](../../../docs/ideas/_TEMPLATE.md) に沿って1施策1ファイルで書く。

複数施策を並べて比較する場合は、以下の表を [strategy/](../../../docs/strategy/) 側に置く。

```markdown
| ID | 施策名 | 群 | 対象とする課題 | 根拠 | 前提条件の充足 | 効果（条件付き） | 概算工数 | 効果測定 |
|---|---|---|---|---|---|---|---|---|
| IDEA-001 | | 開発なし | | [ANL-NNN](...) | 未確認1件 | | — | 可 |
| IDEA-002 | | 開発あり | | [ANL-NNN](...) | 不足1件 | | N人日 | 不可 |
```

## 品質基準

- **どの施策が最良かを断定していない**
- **効果が条件付きで書かれている**（「〜が期待できる」で終わっていない）
- **根拠が三次資料だけの施策が含まれていない**
- **未確認事項が空欄でない**
- **測定できない施策に「測定できない」と書いてある**
- **副作用の欄が埋まっている**
- 工数の見積に前提が併記されている
- 見送った施策も削除せず残している
